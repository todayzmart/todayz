# 02 · Architecture

## 1. Folder layout (one local git repo, one folder per future repo)

The user will split folders into GitHub repos later. Until then everything lives in one local repo so a Claude session can change the API and every client in one go. Each top-level app folder must build and test **on its own** (its own `package.json` or `go.mod`, no imports reaching into a sibling app), so the later split is a copy. Every folder may depend on `shared/` and `design/` (D-58); for example the backend reads the event catalogue in `shared/telemetry/events/`.

## 2. Backend (Go)

### 2.1 Shape

One Go module `github.com/todayz/backend` (path placeholder), one binary with sub-commands:

- `todayz api`: HTTP server (all `/v1` namespaces, §3.2)
- `todayz worker`: River job workers (timers, notifications, rollups, payouts, search indexing, coach)
- `todayz migrate up|down|status`
- `todayz seed dev|demo|test` (local, test and staging only, refuses in prod)
- `todayz ai eval <feature>` (recorded fixtures; live model only when the key is set)
- `todayz admin create-super-admin` (one-off, prints nothing secret)

Beanstalk runs two environments from the same image: `api` (web tier behind ALB) and `worker` (worker tier, no ALB). Both scale independently.

- **Risk flags (D-78):** W0-03 creates the `risk_flags` table in the baseline migration, so any package can raise a flag from Wave 1 on (for example offline counter-code links, store strikes, unresolved failed deliveries). W3-02 owns the rules in `internal/risk` and the admin screens.
- **Foreign keys (D-35, D-79):** a migration adds an FK only to a table from an earlier wave or from the same work package. A column pointing at a table built later is created as plain `uuid`. If the target is built by another package in the same wave, the lead adds the FK in one constraints migration at the end of that wave (D-79). If it is built in a later wave, the package that creates the target adds it (D-35).

Rule: domain packages depend on `platform`, never on each other's internals. Cross-domain calls go through a small interface in the caller's package (e.g. `orders` needs `credits.Holder`). Money-moving operations across domains run in **one database transaction** passed through context.

### 2.3 Libraries

| Need | Choice | Why |
|---|---|---|
| Router | `chi` v5 | Small, stdlib `http.Handler`, middleware ecosystem |
| Contract | `oapi-codegen` (strict server) + `kin-openapi` request validation; Redocly CLI bundles | Spec first; TS client from the same file |

| TOTP | `pquerna/otp` | Admin 2FA and counter codes |
| Crypto | stdlib `crypto/aes` (GCM), `crypto/hmac` | Field encryption and keyed lookups (§10) |
| Logs | `log/slog` JSON | Stdlib |
| Traces/metrics | OpenTelemetry Go SDK, OTLP HTTP | Vendor-neutral, Grafana Cloud |
| Errors | `sentry-go` (wired only when `SENTRY_DSN` is set; unset before Wave 5, D-17; until then browser errors go to `POST /v1/client-errors` and Loki) | Grouping, releases, user impact |
| Validation | spec validation + hand-written domain checks | |
| Images | `disintegration/imaging` or libvips via `govips` | Resize to WebP on upload |
| Testing | `testing`, `testify/require`, `testcontainers-go` (PostGIS 16-3.4; the image comes from `TODAYZ_POSTGIS_IMAGE`, multi-arch on arm64, D-86), `go-cmp`, `rapid` (property tests for the ledger) | |
| Lint/security | `golangci-lint`, `gosec`, `govulncheck` | |

No Redis in v1. Rate limits use Cloudflare at the edge plus an in-process token bucket per instance with Postgres-backed counters for OTP (the only limit that must be exact). Caches are in-process (settings, categories) with short TTLs and a Postgres `LISTEN/NOTIFY` invalidation.

### 2.4 Request pipeline (middleware order)

1. Request ID: always a server-generated ULID, returned in `X-Request-Id`. A valid `X-Request-Id` or `cf-ray` from the client (at most 64 characters of `A-Za-z0-9._-`) is kept only as `client_request_id` in the logs. It sits outside Recover, so a panic log carries an ID.
2. Security headers (`nosniff`, `no-referrer`, a deny-all CSP; `Cache-Control: no-store` on `/v1` unless the handler sets its own)
3. Recover (panic → 500, Sentry, metric)
4. OpenTelemetry server span (extract `traceparent` from the client)
5. Real client IP from `CF-Connecting-IP` (only trusted when the request came through Cloudflare; ALB security group accepts Cloudflare IP ranges only)
6. Access log + RED metrics (route template, not raw path)
7. CORS (exact origins: app., business., admin.; locally the same hosts on `todayz.localhost`)
8. Route policy: puts the matched route's declared policy (body limit, idempotency opt-in) in the request context, because steps 9 and 12 run before chi has picked the route
9. Body size limit (1 MB default, 10 MB on routes that declare an upload)
10. Authn (Bearer access token → principal; anonymous allowed on public routes)
11. Rate limit (per principal or IP per route group)
12. Idempotency (opt-in per route through its policy; `Idempotency-Key` is required on money and order mutations; kept 24 h with the response; details in [04-api.md](04-api.md) §1.6)
13. OpenAPI request validation
14. Authz (route action + path scope `{bid}`/`{sid}`, §3), applied per route
15. Handler → domain service → repository

In code the order is `requestid → secheaders → recover → otel → clientip → accesslog → cors → routepolicy → bodylimit → authn → ratelimit → idempotency → validate`, then `authz` per route. Request ID is outermost so every later layer, `recover` included, logs with the ID. W0-03 creates this chain in `platform/httpx` with one slot (file) per middleware in `httpx/mw/`; each package fills only its own file (D-50).

### 2.5 Time

All timestamps `timestamptz` in UTC; displayed in Asia/Kolkata. "Day" and "month" in caps and limits are the IST calendar day and month. A `clock.Clock` interface is injected everywhere; tests use a fake clock to run 30-minute holds in microseconds. River jobs are scheduled at absolute times; every timer handler re-reads the row and checks the state (idempotent; a late or duplicate job does nothing).

### 2.6 Errors and problem codes (D-24)

- Errors are RFC 9457 problem JSON (see [04-api.md](04-api.md) §1).
- One registry: `backend/api/problems/<domain>.yaml`, bundled by `make gen`. Each entry has a code, HTTP status and i18n key. Handlers return only registered codes; a test fails on an unregistered one.
- The code for a refused state change is always `invalid_transition`.
- W0-03 creates `common.yaml`; each work package adds codes in its own domain file.

## 3. Auth and permissions

### 3.1 Tokens and sessions

- OTP verify returns an **access token** (JWT, EdDSA, 15 min, header `kid`, claims: `sub` user id, `aud` app (`customer|business|admin`), `sid` session id, `roles` for admin, `amr` (`otp`, `otp+totp`)). Keys come from `JWT_SIGNING_KEYS` (JSON set of Ed25519 keys with `kid`); new tokens are signed with `JWT_CURRENT_KID`, and older keys stay in the set until their tokens expire.
- It also sets a **refresh token** cookie: opaque 256-bit random, stored hashed (SHA-256) in `sessions`, rotated on each use. Lifetime 30 days (customer, business), 12 h (admin). Reuse of an old refresh token revokes the whole session family (theft detection).
- **Refresh cookies (D-14):** one per app, so signing out of one app never touches another.

  | App | Cookie |
  |---|---|
  | customer | `__Secure-tz_rt_c` |
  | business | `__Secure-tz_rt_b` |
  | admin | `__Secure-tz_rt_a` |

  Each is host-only on the API host (no `Domain` attribute), `Path=/v1/auth`, `HttpOnly`, `Secure`, `SameSite=Strict`. The apps and the API share a registrable domain, so requests between them are same-site. Locally the host is `api.todayz.localhost`.
- Access token is kept in memory in the SPA (not localStorage). On load the app calls `POST /v1/auth/refresh` with `{app}` to get one; the server reads only that app's cookie.
- **Business scope:** business tokens carry no business id. Every business request names the business, and the store where it applies, in the path: `/v1/biz/businesses/{bid}/...` and `/v1/biz/businesses/{bid}/stores/{sid}/...`. The server checks that the store belongs to the business, that the user has an active `staff` row in it, that the role allows the action (§3.3), and that the store is in the staff row's `store_ids` (null = all). A token cannot be reused across businesses.
- **Admin:** OTP + TOTP every login (TOTP secrets encrypted with `TOTP_ENC_KEY`; 10 recovery codes per admin, stored hashed in `admin_recovery_codes`). Refresh lifetime 12 h. Actions marked † in §3.3 require a TOTP re-prompt if the last one is older than 10 minutes (`step-up`).
- **CSRF:** the refresh endpoint checks `Origin` against the allow-list and requires a custom header (`X-TZ-Client`), on top of `SameSite=Strict`. All other mutating endpoints use Bearer tokens (not cookies), so they are not CSRF-able.

### 3.2 Path namespaces (D-10)

| Prefix | Who |
|---|---|
| `/v1/discover/...` | Public, e.g. `/discover/stores/{slug}`, `/discover/stores/{slug}/items`, `/discover/stores/{slug}/reviews` |
| `/v1/me/...` | The signed-in customer |
| `/v1/biz/businesses/{bid}/...` and `/v1/biz/businesses/{bid}/stores/{sid}/...` | Business users |
| `/v1/admin/...` | Admins (field agents under `/v1/admin/field/...`) |
| `/v1/public/...` | Leads and receipts |
| `/v1/auth/...` | Auth |
| `/v1/rum`, `/v1/events` | Telemetry |

- No method + path pair is defined twice; the bundle step fails on a duplicate.
- `/v1/test/clock` (D-80, owned by W0-03) exists in `local` and `test`, so testers can move server time for manual testing of timers and expiries. Staging and prod builds return `404` for it.
- Outside `/v1`: `/healthz`, `/readyz`, `/version`. `/version` is served by the API only in `local` and `test`; the worker's internal port (8181) always serves it.

Managers see KYC masked (last 4 characters). Finance sees payees' UPI ID and bank details masked (last 4 characters) and no KYC. The shop sees the customer's full phone number only while the order is `out_for_delivery` (D-60), and never the order code (D-04). Field agents follow the window above.

## 4. Frontends

### 4.1 Common stack

React 19 + TypeScript (strict) + Vite, TanStack Router (file routes, typed search params), TanStack Query (server state, persisted to IndexedDB for offline reads), Zod (forms and API responses), React Hook Form, `@todayz/ui` components, Lucide icons, FormatJS (ICU messages), `vite-plugin-pwa` (Workbox), MapLibre GL (customer map, admin maps), Sentry browser SDK, `web-vitals`.

Numbers show in Latin digits in all locales (`numberingSystem: "latn"`, `nu-latn`). Native-script digits are a later item ([10-later.md](10-later.md)).

Routes: each package owns its own `src/routes/<area>/` files; `routeTree.gen.ts` is git-ignored and generated (D-50).

No CSS framework: the design system's `bundle.css` + CSS modules for app-specific layout, using tokens only. Stylelint forbids raw hex outside `shared/tokens`.

### 4.2 Customer app (`customer/`)

- Routes: `/` home, `/search`, `/s/:storeSlug` shop, `/p/:storeItemId` product, `/cart`, `/checkout`, `/orders` (online and "In store" tabs), `/orders/:id`, `/wallet`, `/refer`, `/scan` (bill QR), `/r/:token` receipt (C-24), `/account/*`, `/help/*`, `/auth/*`.
- Location in a store (Zustand) persisted to localStorage: lat/lng, label, source (gps/pin/manual), radius.
- Cart in IndexedDB, one store per cart; switching store asks to clear.
- Realtime: an SSE connection while an order is active (`/v1/me/stream`), else push notifications.
- Budget: initial JS ≤ 170 KB gzip; map and scanner code-split and loaded on demand.

### 4.3 Business app (`business/`)

- Phone: bottom tabs (Overview, Orders, Sell, Stock, More). Desktop: sidebar.
- **Offline-first POS and stock**: Dexie (IndexedDB) holds the store catalogue snapshot (items, prices, stock, barcodes), pending sales and pending stock changes (an outbox). Every local write gets a client ULID and a device sequence number. A sync engine sends the outbox in order to `POST /v1/biz/businesses/{bid}/stores/{sid}/sync` when online; the server applies each entry idempotently (unique `(store_id, client_id)`), authorises it as its own action (§3.3), and returns server changes since the device's cursor.
- **Sync cursor (D-36):** catalogue changes come from `catalogue_changes` (`store_id`, `seq`, `entity`, `entity_id`, `op`), kept 30 days. A cursor older than that gets `resync_required`, and the device downloads a full snapshot. `outbox_events` (24 h) is only for SSE replay.
- **Conflicts:** sales always apply (stock may go negative and is flagged "count needed"); sold prices are never rewritten at sync (an offline sale at an old cached price is accepted as recorded, with no risk flag in v1); price changes are last-writer-wins by server time; deletions win over edits.
- **Offline counter code (D-12):** the offline POS stores the typed counter code and the device time with the sale. The device records its clock offset at each online check. At sync the server checks the code against the time step at the recorded time, and links the sale only if: it syncs within `pos_offline_link_max_hours`; the device clock was within 2 minutes of the server's at its last online check; and the code was not used before. Otherwise the sale stays unlinked and the shop sees "Customer link failed". More than `pos_offline_links_risk_per_day` offline links at one store in a day raises a risk flag.
- Order alerts: SSE stream per store + web push + an audible alert loop until the order is opened (user must tap once per session to allow audio, a known browser rule; the UI asks for it on first open).
- Scanner: keyboard-wedge USB/Bluetooth scanners work as text input; camera scanning with the `BarcodeDetector` API where available, ZXing WASM fallback, both lazy-loaded.
- Printing (optional): browser print of an 80 mm receipt layout; Bluetooth ESC/POS printers are later.
- Controls the user's role does not allow are hidden or disabled with "Ask a manager"; the server check (§3.3) is the real gate.

### 4.4 Admin console (`admin/`)

Desktop-first, same stack, plus TanStack Table for large lists, Apache ECharts (lazy) for Pulse charts. Every list is server-paginated with filters in the URL. Every mutation shows who/when in an audit side panel. Field-agent pages are responsive.

### 4.5 Site (`site/`)

Astro (static output), the design system CSS, zero JS by default (islands only for the language switcher and the lead form). Fixes today's iframe wrapper so pages are indexable: real HTML per route, `sitemap.xml`, `robots.txt`, Open Graph images, JSON-LD (`Organization`, `SoftwareApplication`, `FAQPage`). Pages: home, for retailers, how it works, pricing ("Free for now"), about, contact, privacy, terms, and Hindi/Kannada/Telugu/Tamil versions of the home and retailer pages. Lead form posts to `POST /v1/public/leads` (Turnstile protected).

`verify-dist` checks the built site against an allow-list: same-origin hashed island bundles, plus the Turnstile script `https://challenges.cloudflare.com/turnstile/v0/api.js` on the lead-form page only. Any other script or remote `src` fails the check. Leads are read in the admin console on a "Leads" tab of A-03 (`GET /v1/admin/leads`, 04 §2.7).

## 5. Realtime

- Server-Sent Events from the API: `GET /v1/biz/businesses/{bid}/stores/{sid}/stream` (business), `GET /v1/me/stream` (customer, active orders only), `GET /v1/admin/stream` (ops live counters).
- Fan-out: Postgres `LISTEN/NOTIFY` per channel (`store:{id}`, `user:{id}`) so any API instance can deliver an event raised on another. Payloads are small (`{type, id, version}`); clients refetch through Query.
- Heartbeat comment every 25 s (Cloudflare closes idle streams at 100 s). Clients reconnect with `Last-Event-ID`; the server replays from `outbox_events` (kept 24 h, SSE replay only; POS sync uses `catalogue_changes`).
- Fallback: if SSE fails 3 times, poll every 15 s while the screen is visible.

## 6. Maps and geo

- PostGIS `geography(Point,4326)` on stores and addresses; GiST indexes. Radius search with `ST_DWithin`, distance with `ST_Distance`.
- Map tiles: Protomaps PMTiles of India (OpenStreetMap data, ODbL attribution shown) hosted on R2 behind `tiles.todayz.in`, styled with the design system `map-*` tokens. No per-request map API cost.
- Geocoding: PIN code centroids and locality names from open data (India Post PIN directory + OSM place names) loaded into `places`; reverse geocode = nearest place. A paid geocoder is optional later (`GEOCODER_*` env, off by default).
- Store pins are verified by the field agent or owner dragging the pin; distances shown to customers are straight-line in v1 with "~" prefix.
- Location in analytics and demand data is an H3 resolution-8 cell, never a raw point (D-59).
- Area counts (D-81): "wanted nearby" adds up the cells within `insight_wanted_nearby_radius_m` of the store, then applies k ≥ 10 to the total, never to a single cell.

## 7. Search

Postgres only in v1: `pg_trgm` for fuzzy names, `unaccent`, a `tsvector` with weights (name A, brand B, category C, synonyms D), plus a synonyms table for common Indian names ("atta" ↔ "wheat flour", "curd" ↔ "dahi", Hindi transliterations). Query plan: candidate stores within radius (GiST) → store items matching text (GIN) → rank in SQL. Ranking (D-42): filter to in stock, `live` store, within radius; then score = 0.45·text + 0.30·exp(−d / 1.5 km) + 0.10·reliability + 0.10·rating_norm + 0.05·has_offer, with weights read from settings (`search_w_text`, `search_w_distance`, `search_w_reliability`, `search_w_rating`, `search_w_offer`); ties go to the nearer store. There is no freshness term (D-63); stale stock is handled by the coach and the expiry-rate penalty (`shop_expiry_penalty_threshold_bp`). A dedicated engine (Meilisearch/OpenSearch) is an ADR for later if p95 > 200 ms at scale.

## 8. Voice update

Follows the rules for every AI feature ([11-ai-features.md](11-ai-features.md) §1): the output is a draft a person confirms.

1. Business app records up to 15 s (MediaRecorder, Opus) and uploads to `POST /v1/biz/businesses/{bid}/stores/{sid}/ai/voice-stock/drafts` (cashier and above).
2. Backend sends audio to the STT provider (Sarvam, `SARVAM_API_KEY`; supports en, hi, kn, te, ta and code-mixing).
3. Transcript + the store's item names (top 2,000 by sales, as candidates) go to the model named by the `ai_model_fast` setting (default `claude-haiku-5-5`; code never hard-codes a model id), with `ANTHROPIC_API_KEY` and a strict JSON tool schema: `[{action: sale|restock|count|set_price, store_item_id|unmatched_text, quantity, unit, price}]` (D-65). "Out of stock" is a `count` of 0.
4. Backend validates (item exists, quantities sane) and stores a **draft** in `ai_drafts` (feature `voice_stock`) with confidence per line. Nothing changes yet.
5. The app shows the draft as editable lines; the user taps **Confirm** → `POST …/ai/voice-stock/drafts/{draftId}/confirm`. Each line is checked against the user's role (§3.3, D-65); lines the user may not confirm come back disabled ("Ask a manager"). Allowed lines are applied as the matching change: `sale` → a quick POS sale with no customer (`sale_pos` movement, cashier and above), `restock` → `restock` movement, `count` → `count_correction` movement, `set_price` → price change. Per-line outcomes are recorded on the draft.
6. The voice button is hidden (the endpoints return `404`) unless `feature_voice_enabled` and `ai_voice_stock_enabled` are both on and both keys are set; the admin console then shows "Voice: off". Audio is deleted after 7 days; transcripts kept 90 days for quality review.

## 10. Security baseline

- OWASP ASVS level 2 as the checklist (see [08-testing.md](08-testing.md) §8).
- TLS everywhere: Cloudflare Full (strict) to the ALB with an ACM certificate; HSTS (preload after launch). Locally, Caddy with a local CA.
- Security headers from Cloudflare + app: strict CSP per app (no inline scripts; `connect-src` api., tiles., img., Sentry, Grafana Faro not used), `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera and microphone only on business app; camera on customer app for scanning), `frame-ancestors 'none'`.
- Database: RDS in private subnets, encryption at rest (KMS), TLS required, IAM auth for humans, a least-privilege app role (no DDL), a separate migration role, a read-only `grafana_ro` role on a read replica later (on primary with a `statement_timeout` of 5 s in v1).
- Secrets: AWS Secrets Manager → Beanstalk env at deploy; locally `.env.local` (git-ignored, generated by `make setup`); never in the repo; `.env.example` holds names only; `gitleaks` in `make check`. Nothing prints a secret value.
- PII (D-18, D-44): phone, PAN, GSTIN, UPI ID and bank details are encrypted at the application layer (AES-256-GCM, `PII_ENC_KEY`), with an HMAC column (`PII_HASH_KEY`) where lookup is needed (phone). GSTIN and UPI ID also keep a masked copy (last 4 characters) for display. Logs and traces never contain phones, OTPs, codes, tokens or addresses (a slog handler redacts known keys and a test asserts it).
- Order codes (D-04): `orders.code_enc` (AES-256-GCM, `ORDER_CODE_ENC_KEY`), decrypted only for the owning customer's GET; `orders.code_hmac` (`ORDER_CODE_HMAC_KEY`) for lookup when the shop types the code. The API never sends the plain code to the shop.
- Other codes: OTPs stored hashed; OTP and order codes compared in constant time with attempt counters in the database. Counter-code device secrets encrypted with `DEVICE_SECRET_ENC_KEY`. Bill QR tokens signed with `BILL_QR_SIGNING_KEY`. Receipt tokens are 128-bit random and expire after 30 days (D-45).
- Uploads: content-type sniffed, size-limited, re-encoded (strips EXIF and anything executable), served from `img.todayz.in` (separate origin).
- Abuse: Cloudflare WAF managed rules, rate limiting rules per path, bot fight mode on site, Turnstile on OTP, device fingerprint (coarse) on referral sign-ups, risk rules (see [03-data-model.md](03-data-model.md) `risk_flags`).
- Audit log for every admin action and every money/role/settings change, append-only (no UPDATE/DELETE grant).
- Backups: RDS automated backups 14 days + PITR, a weekly snapshot copied to a second region; restore drill before launch.
- Data protection: India DPDP Act 2023 basics: consent text at sign-up, purpose-limited use, deletion on request, a grievance contact on the site.
