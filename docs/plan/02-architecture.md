# 02 · Architecture

## 1. Folder layout (one local git repo, one folder per future repo)

The user will split folders into GitHub repos later. Until then everything lives in one local repo so a Claude session can change the API and every client in one go. Each top-level app folder must build and test **on its own** (its own `package.json` or `go.mod`, no imports reaching into a sibling app), so the later split is a copy. Every folder may depend on `shared/` and `design/` (D-58); for example the backend reads the event catalogue in `shared/telemetry/events/`.

## 2. Backend (Go)

### 2.1 Shape

One Go module `github.com/todayz/backend` (path placeholder), one binary with sub-commands:

- `todayz api`: HTTP server (all `/v1` namespaces, §3.2)
- `todayz worker`: River job workers (timers, notifications, rollups, payouts, search indexing, coach), all registered kinds (§2.7)
- `todayz migrate up|down|status`
- `todayz seed dev|demo|test` (local, test and staging only, refuses in prod)
- `todayz ai eval <feature>` (recorded fixtures; live model only when the key is set)
- `todayz admin create-super-admin` (one-off, prints nothing secret)

Beanstalk runs two environments from the same image: `api` (web tier behind ALB) and `worker` (worker tier, no ALB). Both scale independently, with different deploy policies (09 §3, D-96).

- **Risk flags (D-78):** W0-03 creates the `risk_flags` table in the baseline migration, so any package can raise a flag from Wave 1 on (for example offline counter-code links, store strikes, unresolved failed deliveries). W3-02 owns the rules in `internal/risk` and the admin screens.
- **Foreign keys (D-35, D-79):** a migration adds an FK only to a table from an earlier wave or from the same work package. A column pointing at a table built later is created as plain `uuid`. If the target is built by another package in the same wave, the lead adds the FK in one constraints migration at the end of that wave (D-79). If it is built in a later wave, the package that creates the target adds it (D-35).

Rule: domain packages depend on `platform`, never on each other's internals. Cross-domain calls go through a small interface in the caller's package (e.g. `orders` needs `credits.Holder`). Money-moving operations across domains run in **one database transaction** passed through context.

No Redis in v1. Rate limits use Cloudflare at the edge plus an in-process token bucket per instance with Postgres-backed counters for OTP (the only limit that must be exact). Caches are in-process (settings, categories) with short TTLs and a Postgres `LISTEN/NOTIFY` invalidation.

**Redis trigger (D-96).** Add ElastiCache Serverless (Valkey) only when one of these is measured: rate-limit or cache queries take more than 20% of database load in Database Insights, or `LISTEN/NOTIFY` fan-out limits SSE. Until then, no Redis.

### 2.4 Request pipeline (middleware order)

1. Request ID: always a server-generated ULID, returned in `X-Request-Id`. A valid `X-Request-Id` or `cf-ray` from the client (at most 64 characters of `A-Za-z0-9._-`) is kept only as `client_request_id` in the logs. It sits outside Recover, so a panic log carries an ID.
2. Security headers (`nosniff`, `no-referrer`, a deny-all CSP; `Cache-Control: no-store` on `/v1` unless the handler sets its own)
3. Recover (panic → 500, Sentry, metric)
4. OpenTelemetry server span (extract `traceparent` from the client)
5. Real client IP from `CF-Connecting-IP` (only trusted when the request came through Cloudflare; ALB security group accepts Cloudflare IP ranges only)
6. Access log + RED metrics (route template, not raw path)
7. CORS (exact origins: app., business., admin.; locally the same hosts on `todayz.localhost`). `/v1/public/*` has its own rule: the marketing site origins only (`todayz.in`, `www.todayz.in`, locally `todayz.localhost`), POST and OPTIONS, no credentials; the site origin never gets a credentialed response on any other route (D-102)
8. Path guard: `400 bad_request` for a raw path that two routers could read differently (one that is not the canonical encoding of its decoded form, or carries an encoded slash `%2F` or a backslash `%5C`), so chi and the validator always see one path (D-100)
9. Route policy: puts the matched route's effective policy (body limit, idempotency opt-in) in the request context, because step 10 runs before chi has picked the route. The policy is the contract's `x-idempotency`/`x-upload` merged with what the code declares; the stronger rule wins, and code weaker than the contract fails startup (D-100)
10. Body size limit (1 MB default, 10 MB on routes that declare an upload)
11. Authn (Bearer access token → principal; anonymous allowed on public routes). An unauthenticated call to `/v1/me`, `/v1/biz` or `/v1/admin` ends here with 401 and never sees a field name
12. Rate limit (per principal or IP per route group)
13. chi picks the route: 404 for an unmounted path, 405 with `Allow` (mounted methods only) for an unmounted method; nothing below runs for either
14. OpenAPI request validation, on the route chi picked: `422 validation_failed` with prefixed field paths; the JSON decoder refuses trailing data, more than 10,000 values or an array past its `maxItems` (`400 bad_request`); at most 50 field errors are listed (`fieldsTruncated`) (D-100)
15. Idempotency (opt-in per route through its policy; `Idempotency-Key` is required on money and order mutations; kept 24 h with the response; details in [04-api.md](04-api.md) §1.6). It runs after validation so a refused request is never stored or replayed
16. Authz (route action + path scope `{bid}`/`{sid}`, §3), applied per route
17. Handler → domain service → repository

In code the order is `requestid → secheaders → recover → otel → clientip → accesslog → cors → pathguard → routepolicy → bodylimit → authn → ratelimit`, then chi routes, then `validate → idempotency → authz` on every mounted route (D-100: one router decides, authn before validation, validation before idempotency). Request ID is outermost so every later layer, `recover` included, logs with the ID. W0-03 creates this chain in `platform/httpx` with one slot (file) per middleware in `httpx/mw/`; each package fills only its own file (D-50).

### 2.5 Time

All timestamps `timestamptz` in UTC; displayed in Asia/Kolkata. "Day" and "month" in caps and limits are the IST calendar day and month. A `clock.Clock` interface is injected everywhere; tests use a fake clock to run 30-minute holds in microseconds. River jobs are scheduled at absolute times; every timer handler re-reads the row and checks the state (idempotent; a late or duplicate job does nothing).

### 2.6 Errors and problem codes (D-24)

- Errors are RFC 9457 problem JSON (see [04-api.md](04-api.md) §1).
- One registry: `backend/api/problems/<domain>.yaml`, bundled by `make gen`. Each entry has a code, HTTP status and i18n key. Handlers return only registered codes; a test fails on an unregistered one.
- The code for a refused state change is always `invalid_transition`.
- W0-03 creates `common.yaml`; each work package adds codes in its own domain file.

### 2.7 Background jobs (D-95)

Every background job is a registered kind, declared with `jobs.Define(jobs.Kind{...})` in `internal/platform/jobs` (W1-11). A test fails if a River worker is registered anywhere else. Adding a job is one declaration plus a handler.

| Kind field | Meaning |
|---|---|
| `Name`, `Owner`, `Description` | Unique name, the owning work package (WP id), one sentence |
| `Class` | `timer` (order and hold expiries), `money` (ledger, payouts, credit expiry), `notify`, `marketing`, `ai`, `rollup`, `maintenance` (partitions, retention) |
| Trigger | `Schedule` (cron expression in IST) or event-triggered |
| `Timeout`, `MaxAttempts`, `Queue`, `Concurrency` | Run limits. `Timeout` is at most 60 s unless the kind is `Batched` (§2.8, D-98) |
| `Batched` | The kind works in batches of at most 60 s, commits a checkpoint per batch and calls `jobs.Yield(ctx)` between batches (§2.8). Payouts, marketing sends, rollup backfills and AI batch jobs are batched kinds |
| `UniqueBy` | The period key for scheduled kinds, so a period runs at most once |
| `Runbook` | Required for the `timer` and `money` classes |

- A handler returns `jobs.Result{Summary map[string]int64, Note string}`, for example `{"sent":120,"skipped":3}`. The jobs middleware writes the run (`job_runs`), the hourly stats (`job_stats_hourly`) and the metrics (05 §8). A run ends `succeeded`, `failed`, `cancelled`, `skipped`, `discarded`, `missed` or `yielded` (a batched kind that stopped at a shutdown and enqueued its continuation, §2.8).
- Scheduled, manual, retry and backfill runs are always logged. Event-triggered kinds (per-order timers, per-message sends) log only failed, retried and discarded attempts; successes are counted.
- `jobs_watchdog` runs every 5 minutes and marks a scheduled kind `missed` when it has no succeeded run within 2× its interval (daily kinds: 15 minutes of grace).
- `timer` kinds can never be paused or run by hand. `money` kinds need `super_admin` with step-up. Every other kind needs `admin` or above. All controls are audited (§3.3).
- `ai` kinds write drafts only. `marketing` and `notify` kinds read their caps and quiet rules from the settings 01 defines.
- Every job already in the plan is a registered kind with its class, owned by the same work package as before: the 05 §3 rollups, `store_reliability`, `store_rating`, `ledger_reconcile`, order timers, notifications, payouts, partition maintenance and the AI jobs.
- D-101 adds four kinds, all owned by W3-16: `asks_close_window` (`timer`, event-triggered at each recipient's `reply_by`: closes that store's window and, after the last one, the ask; it has a runbook), `asks_retention` (`maintenance`, nightly: deletes asks older than `ask_retention_days`; their recipients, replies and store blocks go by `on delete cascade`, and `orders.ask_reply_id` is set to null, 03 §9), and `rollup_ask_demand` and `site_marquee_build` (`rollup`, 05 §3).
- Everything works locally under the test clock; `make demo` runs jobs so A-21 has data.

### 2.8 Graceful shutdown (D-98)

**Rule.** No deploy, scale-in or restart cuts off an API request or a running job. Work W0-03b (07) makes the lead follow-ups below; the rest sits with the owners named in the last table.

**API, on SIGTERM**

1. `/readyz` flips to 503 at once (a draining flag, body `status: "draining"`). `/healthz` stays 200.
2. The server keeps serving for `SHUTDOWN_PRESTOP` (15 s deployed, 1 s locally) so the load balancer's health checks and deregistration stop new traffic.
3. Every SSE stream gets a final `event: reconnect` with `retry: 1000` and is closed. Clients reconnect to another instance (§5).
4. `srv.Shutdown` waits for in-flight requests for up to `SHUTDOWN_DRAIN` = 75 s. It must exceed `WriteTimeout` (60 s); a test holds the two together, like the idempotency lease test (04 §1.6).
5. Request contexts never derive from the signal context. `BaseContext` is a background context that SIGTERM does not cancel. A test sends SIGTERM during an in-test slow handler (the test registers its own route; `/v1/test/slow` belongs to W1-07 and is not a Wave 0 dependency), expects 200, and expects a new `/readyz` call to get 503.
6. Then, in order: stop in-process background loops (`LISTEN/NOTIFY`, caches), close the DB pool, flush telemetry (5 s).
7. Deploy timings: ALB deregistration delay 75 s, container stop timeout 120 s (09 §3).

**Worker, on SIGTERM**

1. `/readyz` goes to 503 and the worker stops fetching new jobs (River `Stop`).
2. Job timeouts cap at 60 s. The registry (§2.7) rejects any `Timeout` above 60 s unless the kind is `Batched`. A batched kind works in batches of at most 60 s, commits a checkpoint per batch and calls `jobs.Yield(ctx)` between batches. While the worker drains, `Yield` enqueues a continuation for the remaining work and returns, and the run ends `yielded`. Nothing is aborted. The continuation is a new run with `trigger` `continuation`. Its unique key is the period key plus the checkpoint sequence (`<period>#<n>`), so River's uniqueness does not drop it while the original run is still `running`.
3. `queue.Drain(c, grace=90s, hardGrace=30s)` runs the whole worker drain: River `Stop` waits up to `DrainGrace` (90 s, more than the 60 s job cap), then `StopAndCancel` gets `hardGrace` (30 s). The total is 120 s, under the 180 s container stop timeout.
4. Hard cancel is a last resort: `StopAndCancel`, with 30 s to return. It logs at error level, counts `tz_job_hard_cancelled_total{kind}` and fires the "Job hard-cancelled at shutdown" alert (warning, with a runbook). The cancelled attempt is retried. This is safe because every job is idempotent, and side effects (an SMS, a push, a ledger post) carry an idempotency key, so a retry never sends or posts twice.
5. Container stop timeout is 180 s.
6. Deploys are immutable: new instances are healthy before old ones get SIGTERM. River's leader election hands periodic scheduling over.

**Database migrations** run before deploy as expand, migrate, contract (09 §3), so draining old instances keep working against the new schema.

**Frontends**
- No forced reloads: the update toast lets the user choose. This holds for a client below the minimum version too (01 §17): it shows "Update available" and reloads when the user taps.
- The POS (B-05) and checkout (C-11) defer the update prompt while a sale or checkout is open (06).
- The service worker precaches every chunk of its own version, so a tab still running the old version keeps working after a Pages deploy removes the old assets.

**Local.** `make stop` (`infra/local/proc.sh`) sends SIGTERM and waits for the same drain (bounded at 180 s for the worker) before it sends SIGKILL.

| Item | Owner |
|---|---|
| `/readyz` draining flag on both processes (`internal/platform/health`); API steps 1, 2 and 4–6 (`lifecycle`, `httpx`, telemetry flush, `cmd/todayz`); the `SHUTDOWN_DRAIN` vs `WriteTimeout` test; `queue.Drain(c, grace=90s, hardGrace=30s)` and `tz_job_hard_cancelled_total` (`internal/platform/queue`); the `proc.sh` ordered stop (`stop-all` stops `api` and `worker` first, waits for them, then stops the rest, mocks last) | W0-03b (lead follow-up) |

## 3. Auth and permissions

### 3.1 Tokens and sessions

- OTP verify returns an **access token** (JWT, EdDSA, 15 min, header `kid`, claims: `sub` user id, `aud` app (`customer|business|admin`), `sid` session id, `roles` for admin, `amr` (`otp`; the admin `otp+totp` is gone, D-264)). Keys come from `JWT_SIGNING_KEYS` (JSON set of Ed25519 keys with `kid`); new tokens are signed with `JWT_CURRENT_KID`, and older keys stay in the set until their tokens expire.
- It also sets a **refresh token** cookie: opaque 256-bit, stored hashed (SHA-256) in `sessions`, rotated on each use. Lifetime 30 days (customer, business), 12 h (admin). Reuse of an old refresh token revokes the whole session family (theft detection). A rotation's new token is derived (HMAC under `PII_HASH_KEY`) from the presented token and a salt stored on the rotated row, so a retry whose response was lost, within `RotationGrace` (30 s) and before the new token is used, gets the same new token back; once it is used, the retry is a 401 that keeps the cookie, and after the window it is reuse (D-105, D-239).
- **Refresh cookies (D-14):** one per app, so signing out of one app never touches another.

  | App | Cookie |
  |---|---|
  | customer | `__Secure-tz_rt_c` |
  | business | `__Secure-tz_rt_b` |
  | admin | `__Secure-tz_rt_a` |

  Each is host-only on the API host (no `Domain` attribute), `Path=/v1/auth`, `HttpOnly`, `Secure`, `SameSite=Strict`. The apps and the API share a registrable domain, so requests between them are same-site. Locally the host is `api.todayz.localhost`.
- Access token is kept in memory in the SPA (not localStorage). On load the app calls `POST /v1/auth/refresh` with `{app}` to get one; the server reads only that app's cookie.
- **Business scope:** business tokens carry no business id. Every business request names the business, and the store where it applies, in the path: `/v1/biz/businesses/{bid}/...` and `/v1/biz/businesses/{bid}/stores/{sid}/...`. The server checks that the store belongs to the business, that the user has an active `staff` row in it, that the role allows the action (§3.3), and that the store is in the staff row's `store_ids` (null = all). A token cannot be reused across businesses.
- **Admin:** SMS OTP every login, no second factor (D-264). Refresh lifetime 12 h. Actions marked † in §3.3 require a **step-up** if the last one is older than 10 minutes: a fresh SMS code to the admin's own number (`POST /v1/auth/step-up/send`, then `/verify`), which stamps the sign-in's session (`sessions.step_up_at`, copied on refresh); the access token does not change. The fifth wrong step-up code ends the admin's admin-app sessions. SMS step-up does not protect against a SIM swap (accepted, D-264).
- **CSRF:** the refresh endpoint checks `Origin` against the allow-list and requires a custom header (`X-TZ-Client`), on top of `SameSite=Strict`. All other mutating endpoints use Bearer tokens (not cookies), so they are not CSRF-able.

### 4.3 Business app (`business/`)

- Phone: bottom tabs (Overview, Orders, Sell, Stock, More). Desktop: sidebar.
- **Offline-first POS and stock**: Dexie (IndexedDB) holds the store catalogue snapshot (items, prices, stock, barcodes), pending sales and pending stock changes (an outbox). Every local write gets a client ULID and a device sequence number. A sync engine sends the outbox in order to `POST /v1/biz/businesses/{bid}/stores/{sid}/sync` when online; the server applies each entry idempotently (unique `(store_id, client_id)`), authorises it as its own action (§3.3), and returns server changes since the device's cursor.
- **Sync cursor (D-36):** catalogue changes come from `catalogue_changes` (`store_id`, `seq`, `entity`, `entity_id`, `op`), kept 30 days. A cursor older than that gets `resync_required`, and the device downloads a full snapshot. `outbox_events` (24 h) is only for SSE replay.
- **Conflicts:** synced sales always apply; the POS never sells past available, so stock goes negative only when offline devices race for the same units, and then reads 0 flagged "count needed" (D-270); sold prices are never rewritten at sync (an offline sale at an old cached price is accepted as recorded, with no risk flag in v1); price changes are last-writer-wins by server time; deletions win over edits.
- **Offline counter code (D-12):** the offline POS stores the typed counter code and the device time with the sale. The device records its clock offset at each online check. At sync the server checks the code against the time step at the recorded time, and links the sale only if: it syncs within `pos_offline_link_max_hours`; the device clock was within 2 minutes of the server's at its last online check; and the code was not used before. Otherwise the sale stays unlinked and the shop sees "Customer link failed". More than `pos_offline_links_risk_per_day` offline links at one store in a day raises a risk flag.
- Order alerts: SSE stream per store + web push + an audible alert loop until the order is opened (user must tap once per session to allow audio, a known browser rule; the UI asks for it on first open).
- Scanner: keyboard-wedge USB/Bluetooth scanners work as text input; camera scanning with the `BarcodeDetector` API where available, ZXing WASM fallback, both lazy-loaded.
- Printing (optional): browser print of an 80 mm receipt layout; Bluetooth ESC/POS printers are later.
- Controls the user's role does not allow are hidden or disabled with "Ask a manager"; the server check (§3.3) is the real gate.

## 5. Realtime

- Server-Sent Events from the API: `GET /v1/biz/businesses/{bid}/stores/{sid}/stream` (business), `GET /v1/me/stream` (customer, active orders and open asks, D-101), `GET /v1/admin/stream` (ops live counters).
- Fan-out: Postgres `LISTEN/NOTIFY` per channel (`store:{id}`, `user:{id}`) so any API instance can deliver an event raised on another. Payloads are small (`{type, id, version}`); clients refetch through Query.
- Heartbeat comment every 25 s (Cloudflare closes idle streams at 100 s). Clients reconnect with `Last-Event-ID`; the server replays from `outbox_events` (kept 24 h, SSE replay only; POS sync uses `catalogue_changes`).
- Fallback: if SSE fails 3 times, poll every 15 s while the screen is visible.
- Shutdown (D-98): on SIGTERM each stream gets a final `event: reconnect` with `retry: 1000`, then closes. A reconnect is not a failure: it does not count toward the 3 failures that start polling, and the client resumes with `Last-Event-ID` on another instance. The hub (W2-05) owns this; SC-GS-07.

## 6. Maps and geo

- PostGIS `geography(Point,4326)` on stores and addresses; GiST indexes. Radius search with `ST_DWithin`, distance with `ST_Distance`.
- Map tiles: Protomaps PMTiles of India (OpenStreetMap data, ODbL attribution shown) hosted on R2 behind `tiles.todayz.in`, styled with the design system `map-*` tokens. No per-request map API cost.
- Geocoding: PIN code centroids and locality names from open data (India Post PIN directory + OSM place names) loaded into `places`; reverse geocode = nearest place. A paid geocoder is optional later (`GEOCODER_*` env, off by default).
- Store pins are verified by the field agent or owner dragging the pin; distances shown to customers are straight-line in v1 with "~" prefix.
- Location in analytics and demand data is an H3 resolution-8 cell, never a raw point (D-59).
- Area counts (D-81): "wanted nearby" adds up the cells within `insight_wanted_nearby_radius_m` of the store, then applies k ≥ 10 to the total, never to a single cell.

## 7. Search

Postgres only in v1: `pg_trgm` for fuzzy names, `unaccent`, a `tsvector` with weights (name A, brand B, category C, synonyms D), plus a synonyms table for common Indian names ("atta" ↔ "wheat flour", "curd" ↔ "dahi", Hindi transliterations). Query plan: candidate stores within radius (GiST) → store items matching text (GIN) → rank in SQL. Ranking (D-42): filter to in stock, `live` store, within radius; then score = 0.45·text + 0.30·exp(−d / 1.5 km) + 0.10·reliability + 0.10·rating_norm + 0.05·has_offer, with weights read from settings (`search_w_text`, `search_w_distance`, `search_w_reliability`, `search_w_rating`, `search_w_offer`); ties go to the nearer store. There is no freshness term (D-63); stale stock is handled by the coach and the expiry-rate penalty (`shop_expiry_penalty_threshold_bp`). A dedicated engine (Meilisearch/OpenSearch) is an ADR for later if p95 > 200 ms at scale.

## 8. Voice update

Follows the rules for every AI feature ([11-ai-features.md](11-ai-features.md) §1): the output is a draft a person confirms.

1. Business app records up to 15 s (MediaRecorder, Opus) and uploads to `POST /v1/biz/businesses/{bid}/stores/{sid}/ai/voice-stock/drafts` (cashier and above).
2. Backend sends audio to the STT provider (Sarvam, `SARVAM_API_KEY`; supports en, hi, kn, te, ta and code-mixing).
3. Transcript + the store's item names (top 2,000 by sales, as candidates) go to the model named by the `ai_model_fast` setting (default `claude-haiku-5-5`; code never hard-codes a model id), with `ANTHROPIC_API_KEY` and a strict JSON tool schema: `[{action: sale|restock|count|set_price, store_item_id|unmatched_text, quantity, unit, price}]` (D-65). "Out of stock" is a `count` of 0.
4. Backend validates (item exists, quantities sane) and stores a **draft** in `ai_drafts` (feature `voice_stock`) with confidence per line. Nothing changes yet.
5. The app shows the draft as editable lines; the user taps **Confirm** → `POST …/ai/voice-stock/drafts/{draftId}/confirm`. Each line is checked against the user's role (§3.3, D-65); lines the user may not confirm come back disabled ("Ask a manager"). Allowed lines are applied as the matching change: `sale` → a quick POS sale with no customer (`sale_pos` movement, cashier and above), `restock` → `restock` movement, `count` → `count_correction` movement, `set_price` → price change. Per-line outcomes are recorded on the draft.
6. The voice button is hidden (the endpoints return `404`) unless `feature_voice_enabled` and `ai_voice_stock_enabled` are both on and both keys are set; the admin console then shows "Voice: off". Audio is deleted after 7 days; transcripts kept 90 days for quality review.

**Customer voice search (AI-C5, D-101)** uses the same STT client through one endpoint, `POST /v1/me/ai/voice-search` (04 §2.8), not the draft endpoints, and keeps nothing: the audio is sent to the provider and dropped (no object, no `ai_drafts` row, no audio or transcript in logs or traces), and the transcript and its refine chips go back in the response only. The search runs only when the customer taps search, as a normal `GET /v1/discover/search` with `source=voice`, and only then is the confirmed query logged, exactly as a typed one; an ask sent from it stores that query. The cost guard counts each call. The mic is hidden unless `ai_voicesearch_enabled` is on and the key is set ([01](01-product-rules.md) §11.1).

**Search assist (AI-C2, D-101)** never runs inside `GET /v1/discover/search`. The app calls `POST /v1/me/ai/search-assist` after the results render, only when search returned `refineHint`, with a 3 s model timeout; any failure returns nothing and the results are untouched. No `ai_drafts` row; the cost guard counts each call.

## 10. Security baseline

- OWASP ASVS level 2 as the checklist (see [08-testing.md](08-testing.md) §8).
- TLS everywhere: Cloudflare Full (strict) to the ALB with an ACM certificate; HSTS (preload after launch). Locally, Caddy with a local CA.
- Security headers from Cloudflare + app: strict CSP per app (no inline scripts; `connect-src` api., tiles., img., Sentry, Grafana Faro not used), `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera and microphone only on business app; camera on customer app for scanning), `frame-ancestors 'none'`.
- Database: RDS in private subnets, encryption at rest (KMS), TLS required, IAM auth for humans, a least-privilege app role (no DDL), a separate migration role, a read-only `grafana_ro` role on a read replica later (on primary with a `statement_timeout` of 5 s in v1).
- Secrets: AWS Secrets Manager → Beanstalk env at deploy; locally `.env.local` (git-ignored, generated by `make setup`); never in the repo; `.env.example` holds names only; `gitleaks` in `make check`. Nothing prints a secret value.
- PII (D-18, D-44): phone, PAN, GSTIN, UPI ID and bank details are encrypted at the application layer (AES-256-GCM, `PII_ENC_KEY`), with an HMAC column (`PII_HASH_KEY`) where lookup is needed (phone). GSTIN and UPI ID also keep a masked copy (last 4 characters) for display. Logs and traces never contain phones, OTPs, codes, tokens or addresses (a slog handler redacts known keys and a test asserts it).
- Order codes (D-04): `orders.code_enc` (AES-256-GCM, `ORDER_CODE_ENC_KEY`), decrypted only for the owning customer's GET; `orders.code_hmac` (`ORDER_CODE_HMAC_KEY`) for lookup when the shop types the code. The API never sends the plain code to the shop.
- Other codes: OTPs stored hashed; OTP and order codes compared in constant time with attempt counters in the database. Counter-code device secrets encrypted with `DEVICE_SECRET_ENC_KEY`. Bill QR tokens signed with `BILL_QR_SIGNING_KEY`. Receipt tokens are 128-bit random and expire after 30 days (D-45).
- Uploads: content-type sniffed, size-limited, re-encoded (strips EXIF and anything executable), served from `img.todayz.in` (separate origin).
- Abuse: Cloudflare WAF managed rules, rate limiting rules per path, bot fight mode on site, Turnstile on OTP, device fingerprint (coarse) on referral sign-ups, risk rules (see [03-data-model.md](03-data-model.md) `risk_flags`).
- Audit log for every admin action and every money/role/settings change, append-only (no UPDATE/DELETE grant).
- Backups: RDS is a single instance at launch (D-96 as amended): automated backups 14 days + PITR, deletion protection, a weekly snapshot copied to a second region; restore drill before launch. An AZ failure means a restore from PITR (an estimated 30–60 minutes); Multi-AZ is one Terraform flag when the founder decides.
- A-22 reads AWS through the API instance role with a read-only policy (non-scopable read actions use `Resource: "*"`); Terraform checks the policy against an action allow-list, so it holds no write action (D-97).
- AWS keys stay out of the app (D-97): `internal/ops` builds an AWS client only when `APP_ENV` is `staging` or `prod`, with an explicit EC2 instance-role (IMDS) credential provider and never the SDK's default credential chain. `infra/local/proc.sh` strips every `AWS_*` variable from app processes, so the founder's Wave 5 keys in `.env.local` reach only Terraform and the lead's shell. The worker's one AWS write is `cloudwatch:PutMetricData` into the `TodayZ/Worker` namespace, only in `staging` and `prod` (09 §3.6).
- Data protection: India DPDP Act 2023 basics: consent text at sign-up, purpose-limited use, deletion on request, a grievance contact on the site.
