# 07 · Work packages

Each work package (WP) is sized for one builder agent in one git worktree, typically 0.5–2 days of agent work. A WP lists the folders and files it **owns**. Owning a folder means owning everything under it, so no other WP in the same wave may own that folder, a folder inside it, or a file inside it. The only exception is the per-domain split files below: they always belong to the WP that owns that domain, wherever they sit.

## Ownership rules for shared files

Files that many WPs would otherwise edit are split so each WP owns its own piece (D-50, D-55, D-24, D-35):

- **API spec:** edit only your own domain's files, `backend/api/paths/<domain>.yaml` and `backend/api/schemas/<domain>.yaml`. The bundled `backend/api/openapi.yaml` is generated by `make gen` (Redocly CLI). Nobody edits it and it is not committed.
- **Problem codes:** `backend/api/problems/<domain>.yaml`. W0-03 creates `common.yaml`; each WP adds its codes in its own domain file. A refused state change is always `invalid_transition`.
- **Generated code:** `backend/gen/`, `shared/api-client/` output and the bundled `openapi.yaml` are git-ignored. `make gen` produces them, and every build and check runs `make gen` first.
- **Migrations:** each WP adds new files named `NNNNN_<wp-id>_<what>.sql`. Each WP owns a block of versions, `<wave><wp:2><seq:2>`: W1-02 uses `10201`–`10299`, W2-03 uses `20301`–`20399` (D-89). Wave 0 keeps `00001`–`00099`; `00003` is River's schema (a Go migration in `internal/platform/migrate`). A check fails when a file's number does not match its `<wp-id>`. A migration may add a foreign key only to a table from an earlier wave or from the same WP. A column that points at a table built later in the same wave, or in a later wave, is created as a plain `uuid`. For a target in a later wave, the WP that creates the target table adds the FK constraint in its own migration. For a target in the same wave, the lead writes one constraints migration at the end of that wave, after the last WP merges and before the gate runs, adding every same-wave FK (D-79).
- **SQL queries:** `backend/db/queries/<domain>*.sql`, owned by the domain's WP.
- **Jobs and seed:** W0-03 pre-creates one registry line and one no-op stub per known domain: `backend/internal/jobs/<domain>.go` and `backend/internal/seed/<domain>.go`. Each WP fills only its own stubs. Nobody edits the registries.
- **Permissions:** policy lives in `backend/internal/platform/authz/policy/<domain>.go`, with a golden table per domain. W1-01 owns the policy engine; each WP owns its domain's policy file and golden table. The lead generates `docs/generated/permissions.md`.
- **Product events:** `shared/telemetry/events/<domain>.yaml`, owned by the WP that owns the domain. A screen WP that needs client-only events for its area adds `events/<app>-<area>.yaml`.
- **HTTP middleware:** W0-03 creates the chain in `backend/internal/platform/httpx` with one slot file per middleware in `httpx/mw/`. Each WP fills only its own slot: W0-03 owns `recover`, `requestid`, `clientip`, `cors`, `bodylimit`, `idempotency`, `validate`; W1-01 owns `authn`, `ratelimit`; W1-07 owns `otel`, `accesslog` (RED metrics).
- **Router registration:** each domain exposes `Register(r chi.Router, deps)`. `cmd/todayz/routes.go` is owned by the lead and gets a one-line addition at merge.
- **Frontend routes:** each WP owns its own `<app>/src/routes/<area>/` files. `routeTree.gen.ts` is git-ignored and generated.
- **i18n:** `shared/i18n/messages/<app>/<area>.en.json`, one file per screen area, owned by the WP that owns the area. W1-03 owns the rest of `shared/i18n`.
- **Makefile:** the root `Makefile` is owned by W0-01 and includes `mk/*.mk`. Each WP that needs a target adds its own `mk/<area>.mk`.
- **UI kit:** `shared/ui` is owned by W1-02 in Wave 1. After Wave 1 the lead owns it (D-84): a WP that needs a new or changed component asks the lead, who makes the change on `main` between merges.
- **Ownership not covered elsewhere (D-84):** `qr_standees` W2-10; `support_messages` W2-09; `catalogue_changes` W1-05; `business_documents` W1-04; receipt tokens and the `/me/purchases` API W2-04; C-24 and the C-13 "In store" tab W2-09; B-03 Overview and B-09 Customers W3-03 (B-04 Orders is the business landing page until then); CR-15 W3-01; `shared/ui` after Wave 1 the lead.
- **Grafana:** `infra/grafana/dashboards/<nn>-<name>.json`, one per dashboard; alert rules in `infra/grafana/alerts/<area>.yaml`; runbooks in `docs/runbooks/<alert>.md`.
- **Scenarios and QA:** each WP owns `e2e/scenarios/<AREA>.md` for its builder-written scenarios and `docs/qa/<wp-id>/`.

## 0. Orchestration protocol (the lead follows this)

1. **Start a wave:** for each WP, spawn a builder agent in its own worktree (`Agent` with `isolation: "worktree"`) on branch `wp/<id>-<slug>`, using the brief template below. Start every WP with no unmet dependencies at once.
2. **Contract first:** any WP that adds endpoints commits its own domain spec files (`backend/api/paths|schemas|problems/<domain>.yaml`) as its **first commit**, then messages the lead. The lead merges that commit to `main` early. Frontend WPs in the same wave run `make gen` and build against the generated client and MSW mocks instead of waiting.
3. **Interfaces first:** where a WP depends on another WP in the same wave, the dependency's Go interface and an in-memory fake land in that first commit too. Required early interfaces in Wave 2: W2-01 credits (`Holder`, posting) and W2-07 pricing (`internal/offers/pricing.go`, `Price(ctx, cart) Quote`).
4. **Builder done:** the builder runs `make check` and the WP's scenarios, then writes `docs/qa/<wp-id>/REPORT.md` covering what was built, the test counts, any scenarios not automated, known gaps and screenshots.
5. **Review:** a Code Reviewer agent (and a Security Engineer agent for WPs marked 🔒) reviews the diff against the WP's acceptance criteria and [01-product-rules.md](01-product-rules.md). Findings go back to the builder through `SendMessage`. At most 3 review rounds; after that the lead steps in.
6. **QA:** an Evidence Collector agent runs the WP's manual QA script against the local stack in the browser pane at the device sizes listed. Screenshots go in `docs/qa/<wp-id>/`. Defects go back to the builder.
7. **Merge:** the lead rebases onto `main`, runs `make check`, merges with a squash commit `<wp-id>: <title>`, and adds the router line.
8. **End of wave:** after the last WP merges, the lead writes the wave's constraints migration (`NNNNN_lead_w<n>_constraints.sql`) adding every same-wave FK left as a plain `uuid` (D-79). Then a Reality Checker agent starts from a fresh `make reset`, runs the wave's gate (W2-13 for Wave 2, W3-14 for Wave 3, W4-01 for Wave 4; for Waves 0–1, `make check` plus the wave's scenarios) and the wave's cross-WP scenarios, and lists what is not actually done. A gate runs only the E2E journeys whose **Gate** column in [08-testing.md](08-testing.md) is that wave or earlier. The next wave starts only on a pass.
9. **Plan changes:** if a builder finds that a rule is wrong or missing, it stops and asks the lead. The lead asks the user if the question touches money, codes, timers, permissions or user-visible behaviour, then updates this plan.

### Builder brief template

```
You are building WP <ID> "<title>" for TodayZ.
Read first: /CLAUDE.md, docs/plan/README.md, docs/plan/01-product-rules.md, <folder>/CLAUDE.md, and the plan sections listed below.
Plan sections: <list>
You own: <folders/files>, plus your domain's split files (07 §Ownership rules). Do not modify anything else; if you must, stop and message the lead.
Depends on (already on main): <WPs>.
Deliver: <deliverables>.
Tests required: <tests>. Scenarios to make pass: <IDs from 08-testing.md>.
Definition of done: docs/plan/README.md §Definition of done.
Never print secret env values. Never push or create GitHub repos. Do not commit generated code; run `make gen`. Run `make check` before reporting.
When finished, write docs/qa/<ID>/REPORT.md and reply with a summary, the test counts and any open questions.
```
