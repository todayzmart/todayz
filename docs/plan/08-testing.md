# 08 · Testing

## 1. Test pyramid and where tests live

| Level | Tool | Where | Runs in |
|---|---|---|---|
| Unit (Go) | `go test`, testify, go-cmp, `rapid` (property) | next to code | `make check` |
| Integration (Go + real Postgres/PostGIS) | testcontainers-go, `testkit.NewDB(t)` (a template DB per package, so each test gets a fresh copy in about 50 ms) | `*_integration_test.go` | `make check` |
| Contract | Schemathesis against the running API; MSW mocks generated from the spec; generated-code freshness check | `e2e/contract` | `make check` (short), `make e2e` (full) |
| Component (React) | Vitest + Testing Library + MSW, axe-core | next to components | `make check` |
| Visual | Playwright screenshots of Storybook stories and key screens (en + `en-XA`) | `e2e/visual` | `make e2e` |
| End to end | Playwright (multi-context: customer + shop + admin in one test), against the full local stack with the mocks and the test clock | `e2e/journeys`, `e2e/scenarios` | `make e2e` |
| Load | k6 | `e2e/load` | `make load` |
| Security | gosec, govulncheck, npm audit, gitleaks, ZAP baseline/full, custom abuse tests | `e2e/security` | `make check` (static), `make security` (dynamic) |
| Accessibility | axe in Playwright on every route; manual screen-reader scripts | `e2e/a11y` | `make e2e` |
| AI evals | `todayz ai eval` on recorded fixtures (live model optional) | `backend/internal/ai/*/eval` | `make check` (recorded), `make ai-eval` (live) |
| Manual | Scripts below, run by the QA agent in the browser pane, plus the human founders on real phones before launch | `docs/qa/manual` | per WP + wave 4 |

Coverage targets (enforced): Go domain packages ≥ 85% lines, `credits`, `orders`, `pos`, `authz` ≥ 95% branches; frontend `shared/ui` ≥ 90%, apps ≥ 70%. Coverage is a floor, not the goal: the scenario list is the goal.

## 2. Test infrastructure

- **Test clock (D-80):** in `APP_ENV=local` and `APP_ENV=test`, `POST /v1/test/clock {advance: "31m"}` moves the server clock and waits (up to `wait`, default 10 s, at most 50 s) for the River jobs that became due to run; QA agents use it for manual testing on the local stack. In staging and prod builds the route is not registered: a test asserts it returns 404 in a `staging` and a `prod` build.
- **Test OTP (D-15):** there is no `dev` environment; the environments are `local`, `test`, `staging`, `prod`.
  - In `local` and `test` only, the reserved numbers `+91 90000 000xx` accept `000000`. A test asserts that a `staging` or `prod` build treats them like any other number (`000000` refused).
  - Every other number goes through the mock SMS server. Sends to reserved numbers (OTP and notification SMS) also go to the mock and show in the mocks UI; the only shortcut is that verification accepts `000000`. Tests and QA agents read the OTP from the mocks UI/API at `mocks.todayz.localhost`, never from a log.
  - An OTP is never logged in any environment, including `local` and `test` (AU-15).
- **No real keys (D-17):** the default suite (`make check`, `make e2e`) runs with every provider key unset. SMS, push, Sentry, Anthropic and Sarvam go to the mocks or local tools (PL-04). Live AI evals (`make ai-eval`) and manual AI QA use real keys only if the user puts their own in `.env.local`.
- **Fixtures:** `todayz seed test` builds a small deterministic world: 2 cities; stores covering every business status (verified, needs info, suspended) and every store status (`draft`, `pending_review`, `live`, `paused`, `suspended`), pickup only, delivery only, both, and in-store only (both off), auto-accept on, cashback 0/5%; 200 products; customers (new, regular, limited by strikes, high wallet, a wallet with a lot expiring tomorrow, referred-pending, blocked, one with an open order); staff in every role; admins in every role of D-64 (field_agent, support, catalogue, analyst, admin, and two each of finance and super_admin for the two-person approval tests); all enrolled, plus one unenrolled admin so A-01 first-login enrolment can be tested. Their deterministic TOTP secrets live in `e2e/fixtures/admins.yaml`, never in docs or logs. The backend does not read `e2e/`: `infra/local/local.env` sets `SEED_ADMINS_FILE=e2e/fixtures/admins.yaml`, the seed module reads that path, with the variable unset it seeds no TOTP admins and logs the variable's name, and it refuses to run unless `APP_ENV` is `local` or `test`.
- **Insights fixtures (D-99):** `seed dev`, `seed demo` and `seed test` all make every Demand insights kind fire, so a tester sees them locally. They are three groups of rows plus search and bill history; the book lists them as `<seed:insights-SL>`, `<seed:insights-SL2>` and `<seed:price-compare>` ([qa/manual/README.md](../qa/manual/README.md) §7), and `seed test` builds the same rows with dates relative to the test clock.
  - **Sri Lakshmi (the original kinds):** selling fast (Amul Butter 100 g: 56 sold in the last 7 days, 10 on hand, so 1.25 days of stock and high severity), sitting on the shelf (Toor dal 1 kg: 8 in stock, last sale 26 days ago, cost known), going to waste (the Curd 400 g batch of 10 expiring in 3 days), stock check due (Toor dal 1 kg last confirmed 84 h ago, the only item past `stock_stale_after_hours`), wanted nearby (12 searches for "Horlicks 500 g" and 9 for "Bournvita", both in H3 cell W, 1.2 km from this shop; fewer than 10 other live stores are near, so no "No shop nearby has it."). The card shows Selling fast, Going to waste, Stock check due and Sitting on the shelf; Wanted nearby is read in the Insights tab.
  - **Sri Lakshmi 2 (the insights shop; every other kind, 13 rows in the tab):** selling fast (Tata Tea Gold 250 g: 64 sold, 12 on hand), sitting on the shelf (Mango pickle, last sale 23 days ago; Agarbatti, 40 days), going to waste (a set of 4 items to test "+ 1 more": Curd 200 g tomorrow, Buttermilk, Cheese slices, Fresh cream in 4 days), wanted nearby (two rows: Horlicks 500 g with 12 searches in cell W, 1.2 km from this shop, and Boost 500 g with 11 in cell S2, 0.2 km from it and 2.6 km from Sri Lakshmi, which a neighbour stocks; Bournvita with 9, also in W, is under the 10-search floor and has no row; fewer than 10 other live stores are near, so never "No shop nearby has it."), missed sales (Idli rice closes at 0 on 20 and 21 Oct (2 whole days; today does not count), 4 units sold one a day on 16, 17, 18 and 20 Oct, with 24 matching searches in cell S2 of which 18 on those two days), expired on shelf (Paneer: a batch of 6 that expired on 21 Oct and a second batch of 4 that expires on 28 Oct), selling below cost (Sunflower oil at ₹140 against the latest batch with a cost, ₹146, with an older ₹150 batch ignored; Salt 1 kg at ₹24, MRP ₹28, whose latest batch cost ₹240 is a case price entered as a unit price, so the row reads "Check the cost entry for Salt 1 kg"), stock check due (6 in-stock items last confirmed 9 days ago), bought together (Bread with Eggs: 21 of Bread's 84 bills, Eggs in 70, 600 bills in the 60 days, share 25%, lift 2.14; and a decoy, Nandini Toned Milk 500 ml in 480 of the 600 bills with Parle-G in 300, 240 together, share 50% and lift 1.0, which must not fire at the default lift; the rollup stores it, because it filters on the bill floor only, and it shows once `insight_pair_min_lift_pct` is lowered to 100), and regulars slipping away (11 phone-linked customers, 8 with 3+ visits in 60 days and none for 22 days). Every other item is confirmed at the clock time. Tata Tea, the milk (56 sold in 7 days, 15.0 days of stock) and Parle-G (35 sold, 16.0 days) are the only items with 5 or more sales in 7 days, so at `insight_cover_days` 14 only Tata Tea fires; at `insight_pair_min_lift_pct` 100 the milk pair is the only row added. The card shows Selling fast, Going to waste, Expired on shelf and Selling below cost.
  - **Chennai (priced above nearby):** one shop priced above the median of 12 other live verified stores, each of a different business ("Chennai Store 01" to "Chennai Store 12"), for one product, and a second product listed by only 9 of them (below the 10-store floor). The same 12 stores make "No shop nearby has it." testable: 14 searches for "Horlicks 500 g" near the shop and none of the 12 lists it, all 14 in H3 cell M, about 0.5 km from the shop. The priced-above kind stays off until Q-52 is decided; tests switch `insight_price_compare_enabled` on.
  - The seed runs the rollups once at the end (`todayz rollup --from --to`) so `rollup_item_pairs` (with `bills_total` and `lift_bp`) and the search demand exist at once. **Every seeded search is placed in a named H3 resolution-8 cell** (W, S2, M), chosen so its centre is at most 1.5 km from the shop it counts for and at least 2.5 km from the other (a shared cell: at most 1.5 km from both); the seed computes these distances when it builds and fails, naming the cell, the shop and the distance, if a bound is broken ([qa/manual/README.md](../qa/manual/README.md) §6). Dates are relative to the test clock; every threshold in the rows above has at least half a day of margin.
- **Ask fixtures (D-101):** `seed dev`, `seed demo` and `seed test` build the world the ASK book uses (`<seed:asks>`, `<seed:ask-gaps>`, `<seed:site-marquee>` in the manual README §7), relative to the clock. The master product "LED bulb 9 W" (Electricals, MRP ₹120) is listed only at Annapurna Provisions (₹110, 2 on hand, stock confirmed 5 days ago, so stale); Nandi Hardware lists "Extension board 4 socket" (Electricals) and no bulb. Sri Lakshmi is the only Bengaluru store that lists Amul Butter 100 g. Customers C51–C55 hold the ask states (none; 4 asks today; 20 asks in a row with no Yes and no collected or delivered online order since; reported by Sri Lakshmi; one open ask). Nandi Hardware has received 5 asks today. U01–U12 asked for "Kodo millet 1 kg" in Bengaluru in the last 7 days with no Yes, and U01–U09 asked for "Foxtail millet 500 g". `search_performed` events with a `product_id` in Bengaluru in the last 7 days: Amul Butter 100 g by 15 distinct signed-in searchers, Maggi 70 g by 12, Dolo 650 by 20 (a denylisted category) and Toor dal 1 kg by 9, plus Toor dal by 6 anonymous devices that never count towards the floor. Hyderabad has none.
- **Slow route and slow query:** `/v1/test/slow?ms=` and `/v1/test/slow-sql?ms=` (04 §2.9, same gate as the test clock) force a slow request or a slow query for the latency alerts and the slow-network checks.
- **Factories:** Go `testkit/factory` and TS `e2e/factory` create any entity through the API (not SQL) so tests exercise real rules.
- **Isolation:** each E2E worker gets its own city slice of the seed (prefix-based) so tests run in parallel without collisions.
- **Flake policy:** a test that fails then passes on retry is marked flaky automatically and quarantined; the WP owner fixes it within the wave. Zero quarantined tests at wave exit.
