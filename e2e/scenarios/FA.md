# Field agent scenarios (SC-FA)

FA-01…FA-15 belong to W3-06 (`admin/src/field`, `backend/internal/business/agent*.go`, api `admin-field`). They are builder-written, with at least one scenario per A-04 and A-15 acceptance criterion in [06-screens.md](../../docs/plan/06-screens.md) and per field rule in [01-product-rules.md](../../docs/plan/01-product-rules.md) (D-39, D-47, D-64). The format follows 08 §3: `ID · Given / When / Then · level`, where U is unit, I is integration, E is E2E and M is manual. Go tests are in `backend/cmd/todayz/field_http_test.go`, admin unit tests in `admin/src/field/field.test.tsx`, and Playwright journeys in `admin/e2e/field.spec.ts` (360 px phone).

| ID | Scenario | Lv | Where |
|---|---|---|---|
| FA-01 | Given a field agent, when they start a shop with a name and the owner's number, then the business is a draft with `onboarded_by` set to the agent, it is not confirmed, and the request carried an Idempotency-Key (required: 400 without it; a replay with the same key gives the same draft and no second invite). A number that is not a 10-digit Indian mobile is refused on the phone before any call. The agent's own number is refused by the API (422 `body.ownerPhone`). | I, U, E | `TestFieldOnboardingHTTP`; `field.test.tsx` "checks the owner number before creating"; `field.spec.ts` A-04 |
| FA-02 | Given a shop with no category or no complete store, when the agent asks for the owner's code, then the API answers 409 `submit_incomplete` with the missing fields and sends no SMS, and the wizard sends the agent to the step that fixes it | I, U, E | `TestFieldOnboardingHTTP`; `field.test.tsx` "Finish the store"; `field.spec.ts` A-04 ("Add the category") |
| FA-03 | Given a ready shop, when the code is sent, then the owner's number is shown masked, the expiry is shown, and resending waits out `resendAfterSeconds`. When the owner reads out a wrong code, then the agent sees how many tries are left. When they read out the right code, then the business is `submitted`, `ownerConfirmed` is true, and the owner can see it in the business app. | I, U, E | `TestFieldOnboardingHTTP`; `field.test.tsx` "sends the owner a code"; `field.spec.ts` A-04 |
| FA-04 | Given a shop's store inside the edit window, when the agent searches the catalogue and adds a master product with a price and opening stock, or adds a new product, then it is listed in the store. A new product is `pending_review` (D-64), and a product already in the store is 409 and shown as "Already listed". (Price above the MRP: the catalogue rule refuses it as `validation_failed`, and the wizard words it; no W3-06 test covers it.) | I, U, E | `TestFieldOnboardingHTTP`; `field.test.tsx` "adds from search"; `field.spec.ts` A-04 |
| FA-05 | Given the photos step, when the agent takes a storefront or inside photo, then the API registers it and answers a presigned PUT, the file goes straight to object storage (never through the API), and only shop_photo and storefront are accepted, at most 5 of each. The photo counts only after `.../confirm` finds the file in storage; an upload never confirmed stops using the cap 20 minutes later (on the business-app upload route too) and can no longer be confirmed (409); the hourly `business_field_photos_sweep` then deletes its object and marks it rejected, leaving the owner's own pending uploads alone. Only the shop's agent confirms (another agent 403), and a stored file of another type or larger than declared is 422. A non-image file or one over 10 MB is refused on the phone before any call. | I, U, E | `TestFieldOnboardingHTTP`, `TestFieldPhotosHTTP`, `TestFieldPhotoSweepHTTP`; `field.test.tsx` "uploads a photo", "refuses a large photo", "confirm fails"; `field.spec.ts` A-04 |
| FA-06 | Given a sent code, when five wrong codes are read out, then the sixth try is 429 `otp_locked`. A code older than 5 minutes is 401 `otp_expired`. A new owner number ends the old code. Every wrong try, the lockout, the first try on a locked code and the first try on an expired code (once per code) write `business.owner_code_fail` (no number, no code) and count `tz_field_owner_code_failures_total`. | I | `TestFieldOwnerCodeLimitsHTTP` |
| FA-07 | Given a business another agent onboarded, when an agent reads or changes it, then every field route answers 403 and their list does not show it. A business the shop created itself is not on the field routes (404). | I | `TestFieldEditWindowHTTP` |
| FA-08 | Given a business verified 29 days 23 hours ago, when its agent adds or edits an item, then it is allowed, and so it is at exactly `verified_at` + 30 days. At 30 days and one second, item adds, item edits, stores and photos are refused, the list still reads, and the wizard shows the shop read-only. Raising `field_agent_edit_window_days` (a setting, not a constant) lets the agent back in. An admin is not windowed (D-39). | I, U | `TestFieldEditWindowHTTP`; `field.test.tsx` "closed window is read-only" |
| FA-09 | Given a field agent with onboarded, verified and live shops and items added, when they open A-15, then they see only their own numbers (onboarded, verified, live, products added, in window, first-order rate) and an 8-week trend, from `/v1/admin/field/me/stats`, and the page never calls `/v1/admin/field-agents` | I, U, E | `TestFieldStatsHTTP`; `field.test.tsx` A-15; `field.spec.ts` "A-15: a field agent" |
| FA-10 | Given an admin, when they open A-15, then they see every agent in a table and pick whose weekly trend to show. A field agent who calls `/v1/admin/field-agents` gets 403. The sidebar shows Add shops and Field agents to field agents and admins only (AD-02). | I, U, E | `TestFieldStatsHTTP`; `field.test.tsx` A-15; `field.spec.ts` "A-15: an admin"; `roles.spec.ts` |
| FA-11 | Given an agent who sent 10 owner codes in the last hour (`field_owner_codes_per_agent_hour`), when they send another, to any shop or number, then it is 429 `rate_limited` with Retry-After, and other agents are unaffected. Sign-in codes to the owner's number count towards its 5 an hour. | I | `TestFieldOwnerCodeGuardsHTTP` |
| FA-12 | Given an owner number whose account is blocked, when the agent creates a shop with it, changes to it or sends a code, then it is 422 on `body.ownerPhone` (the same as any refused number) and no SMS goes out. A correct code read out after the account is blocked is the same 422 and the code stays unused. The wizard says the number cannot own a shop. Over the per-agent cap the Retry-After is when the (count − cap + 1)-th oldest send leaves the hour, and two sends at cap − 1 give one 200 and one 429. | I, U | `TestFieldOwnerCodeGuardsHTTP`; `field.test.tsx` "owner number cannot own a shop" |
| FA-13 | Given a correct code, when the shop has lost a required field (`submit_incomplete`), then nothing changes and the code stays unused. When two verifies with the right code race, then one is 200, the other 409, and there is one submit. Another agent sending or verifying is 403. A submitted shop's owner number cannot change (409). | I | `TestFieldOwnerCodeGuardsHTTP`, `TestFieldOnboardingHTTP` |
| FA-14 | Given an item the owner added in the business app, when the agent who onboarded the shop edits it, then it is 403; their own items are editable and an admin can edit both (D-232). The item list marks each item `editable` for the caller, and the wizard shows Edit only on the agent's own items ("Added by someone else" on the others: the shop's, another agent's or an admin's). | I, U | `TestFieldOnboardingHTTP`; `field.test.tsx` "offers Edit only on the items the agent added" |
| FA-15 | Given a rejected or suspended business, when an agent or an admin adds a photo or an item, then it is 403; a store is 409 `invalid_transition`. In A-15 a disabled agent stays in the admin table, marked "Disabled". Removing the `field_agent` role hides the agent from A-15, and their shops drop out of the totals. | I, U, E | `TestFieldPhotosHTTP`, `TestFieldStatsHTTP`; `field.test.tsx` A-15; `field.spec.ts` "A-15: an admin" |

Audit (part of FA-01…06): every field write is audited with the agent as an admin actor, and no audit row, log line or response carries the owner's full number or a code (`TestFieldOnboardingHTTP`, "Audit"). Not covered here: a real SMS to the owner's phone (no provider calls in worker sessions), and capturing a photo with a real phone camera (M, lead's device run).
